# X20 Pro first-run hardware test plan

This is for the later owner-operated session. No physical controller was connected during Phase A. Keep `X20CTL_SCREEN_WRITES` unset until starting this session. Use the stock manufacturer workflow/mode and legitimate recovery material; do not update firmware as part of this test.

## Capture order and stop conditions

1. **Before connecting:** save controller model, hardware/firmware revision, manufacturer mode instructions and package hashes. Photograph the current screen. Preserve any legitimate stock resource. No asset-byte dump command was found in DIYTool; CRC queries cannot back it up.
2. **Connect USB; Detect:** choose X20 Pro → Device → Screen → First-run check. Set the process environment `X20CTL_SCREEN_WRITES=1`, restart X20CTL, turn Simulate off. Detect lists present candidates and COM names. Type the correct COM port explicitly. Save the local detect record. Do not infer association from list order.
3. **Read flash ID (10-second action bound):** record actual TX/RX. Port opens 115200 8N1, DTR/RTS off, no handshake. Expected opening requests are 64-byte `4B 30 4C 54`, nonce at 4, model-derived checksum at 8, E8 17 at 12, baud index 09 at 16, raw CRC of first 32 bytes at 32. After valid 4B response, switch to 1382400 and repeat with index 7F. Replies are modeled as 63 bytes; verify actual lengths, fragmentation and any trailing bytes before continuing.
4. **Identity:** flash query is 64 bytes starting `6D 01 00`, remaining zero. Expected flash reply starts `7D 18 40 EF 00` for enabled profile 0xEF4018. The handshake magic is captured LT7589 0x19717589. If actual identity differs, save the visible ID and stop; unsupported NOR/NAND/address-mode paths must not be guessed.
5. **Dry run:** native 160×80 test image, static, neutral brightness/contrast, no rotation/scaling. Expected image quadrants: red TL, green TR, blue BL, white BR. Press Dry run and review saved JSON. It sends nothing and freezes the nonce for the next upload. Check image payload at 0x410000 and metadata at 0x400000. Each upload region uses 4B30, 4B32, 6D0100, 6C chunks, 6E CRC. Handshake packet CRC is at 32; data packet CRC covers header+payload and is appended LE32.
6. **Before → Upload test image:** mark Before only after recording the old screen. Press once. A 25,612-byte still generates 13 content writes (12×2048 plus 1036), then metadata has two 2048-byte writes. Each 6C packet starts opcode, address LE32 at 1, mode byte at 5 (0/1 alternating), payload length LE16 at 6, data at 8, raw CRC at end. Expected ACK starts `7C 00`. Stop on wrong opcode/status, unexpected identity or CRC. No automatic retries.
7. **CRC:** 6E is 64 bytes, address LE32 at 1, length at 5, requested region CRC at 9, raw CRC of bytes 0..12 at 13, zero tail. Expected progress `7E 30`, final `7E 31` or `7E 32` with actual region CRC LE32 at 2. Compare against saved asset and metadata. The CRC is reflected EDB88320, init zero/no xor; 123456789→2DFD2D88. Metadata is 4096 bytes: 68 45 71 19; kind LE32 3 static / 5 animation; asset length at 8; asset CRC at 12; raw first-16 CRC at 16; animation delay/10 at 20; remaining FF.
8. **After:** photograph actual screen. Confirm all four quadrants and orientation, then restart/reconnect and verify persistence. Mark After and Record result only after observation. Save elapsed time and exact traces. A successful app progress bar is not the physical observation.
9. **Restore stock:** select Confirm reset, press Restore stock once. Expected 11 calls: image-region prologue, four FF at 0x410000 with mode0 and CRC; metadata prologue, two 2048-byte FF writes at 0x400000/0x400800 with modes0/1 and CRC. Metadata query retains four-FF requested CRC DEBB20E3; independently validate returned metadata CRC. Inferred erase cadence predicts 4096-byte sectors at 0x410000 and 0x400000; actual extent, adjacent data and fallback remain physical checks. Restart, photograph default fallback and confirm persistence.
10. **Failure:** timeout/cancel is indeterminate. Do not immediately resend. Use Check transfer (≤100 seconds) to query both attempted-region CRCs through a fresh connection. Matching data means no retry. A valid mismatch permits one explicit Retry once. Unavailable readback keeps retry disabled. Restore always requires its own confirmation; no automatic erase/reset.
11. **Only after static+restore:** upload a short ≤5 FPS GIF. Confirm black transparency, disposal, normalized uniform timing, restart/persistence, then restore again. Do not send the roughly 13 MB Levetop reference UI resource through the artwork uploader.
12. **Battery:** compare stock, static test and short animation with identical backlight, RGB, vibration, connection and workload. Record idle/sleep/wake current or controlled runtime. Screen preview stops at 30 seconds and PC upload is finite; these software defaults do not measure pad power.

## Return bundle

`%LOCALAPPDATA%/X20CTL/Screen/FirstRun` records (detect, identity, exact dry-run, timestamped tx-attempt/tx-complete/rx chunks, upload/error/restore and before/after), original `.x20screen` plus exported `.bin`, model/firmware/mode/package hashes, physical photos/video before/upload/restart/restore, CRC/persistence results, neighboring-data/erase observations if a legitimate read path exists, and battery measurements. A write exception can have sent part of its attempted buffer; preserve both attempted/completed records.

Stop and retain evidence on wrong identity, unexpected frame boundaries, CRC/status disagreement, lost restoration, or effects outside screen artwork. Unset the owner-write environment setting after the session. No firmware flashing, driver installation or arbitrary MCU commands are part of this plan.
